# 起動中の本体の操作

状態：段階 4 は実装済み。

この資料は、自動化用 CLI から常駐中の本体の状態を読み、操作する仕組み(段階 4)の通信の形式と安全性を定める。
CLI 全体の約束と段階の位置づけは [automation-cli.md](automation-cli.md) にあり、この資料はその「段階 4」を詳しくしたものである。

## 目的と範囲

目的は、トレイ、ホットキー、範囲の選択画面、録画中の操作バーの流れを、AI が確かめられるようにすることである。
段階 1〜3 の CLI は、本体を介さずに録画プロセスを使う。このため、本体の状態遷移、選択画面、通知には届かない。

この仕組みで扱うのは次の 3 つである。

- **状態の取得**：録画の状態、開いている画面、トレイメニューの各項目の有効と無効、直近の保存の結果。
- **操作**：`RecorderAction` の 8 つの動作、選択画面の完了と取り消し、本体の終了。
- **待ち合わせ**：状態が条件を満たすまで、本体の側で待って返す。

設定の変更、更新の確認、保存先の確認ダイアログへの応答は扱わない。
設定は設定ファイルと CLI の `settings` で扱えるうえ、更新の確認は配布サーバに依存するためである。

## 有効にする条件

設定の項目 `AutomationEnabled`(既定は無効)で有効にする。
設定画面の「高度な設定」に「自動化用の接続を受け付ける」のチェックボックスを置き、保存した時点でパイプを開閉する(再起動は要らない)。

起動引数と環境変数では有効にしない。
本体は普通、自動起動で起動するので、起動引数を渡す経路がない。2 つ目の起動は多重起動の判定で何もせずに終わるので、後から引数を渡すこともできない。
環境変数は自動起動では設定されず、有効になっていることを利用者が画面で知れない。

既定を無効にするのは、同じユーザーの別のプロセスから録画を始められる口になるためである。
使う人だけが開ける形にする。

## パイプと安全性

### パイプの作り方

- 名前は固定の `ScreenRecorder.Automation` とする。CLI が名前を知る別の手段を持たずに済むためである。
- 最初のインスタンスは `PipeOptions.Asynchronous | CurrentUserOnly | FirstPipeInstance`、バイトのモードで作る。録画プロセスとのパイプと同じ作り方に `FirstPipeInstance` を足したものである。
- `FirstPipeInstance` で作れなかったとき(別のプロセスが同じ名前を先に作っていたとき)は、警告を診断ログに残し、自動化の接続を受け付けない。
- 同時に受け付ける接続は 4 本までとし、最初のインスタンスを閉じずに持ったまま、2 本目以降のインスタンスを作って待つ。`waitFor` で待っている接続があっても、別の接続から `status` や `exit` を送れるようにするためである。
- 接続が切れたインスタンスは、`Disconnect` して同じインスタンスで次の接続を待つ。最初のインスタンスを閉じなければ、その名前を別のプロセスが先に作ることはできない。
- 行の上限は、録画プロセスとの通信と同じ 1 MiB とする。
- 接続してから要求の行を受け取り終えるまで、または前の応答を返してから次の行を受け取り終えるまでの期限を 5 秒とし、過ぎた接続は閉じる。要求を送らずに止まった接続が枠を埋め続けないためである。

### なりすましへの対策

CLI は接続した直後、要求を送る前に、接続先のプロセスを OS から確かめる。
`GetNamedPipeServerProcessId` で接続先のプロセス ID を取り、その実行ファイルのフルパスを読む。
`--app` で本体の場所を指定したときはフルパスが一致すること、指定しないときはファイル名が `ScreenRecorder.exe` であることを確かめ、違えば `impersonatedServer` で止める。
実行ファイルを読めなかったとき(本体を管理者として起動した場合など)は、確かめられないものとして `serverUnverified` で止める。
同じ名前のパイプを別のプロセスが先に作り、CLI の要求を受け取ることを防ぐためである。
`hello` の応答に入るプロセス ID はサーバー自身の申告なので、この確認には使わない。

`--app` を指定しない場合の確認はファイル名だけなので、同じ名前の別の実行ファイルは見分けられない。
同じユーザーの任意のコードは本体を操作できるという前提(次の節)の範囲の制約として受け入れる。

### 認証を足さない理由

接続時のトークンによる認証は足さない。
`CurrentUserOnly` により、接続できるのは同じユーザーのプロセスだけである。そのプロセスは、本体が書いたトークンのファイルも読めるし、ホットキーの送信や本体の起動もできる。
このため、トークンは同じユーザーの任意のコードに対する防御にならない。

代わりに次の 3 つで守る。

- 既定を無効にする。
- 操作を「利用者がトレイとホットキーでできること」に限る。外部への送信を持たない。
- 接続元のプロセス ID を診断ログに残す。

名前付きパイプは、同じユーザーの別のセッション(リモートデスクトップなど)からも届く。これは `CurrentUserOnly` の範囲なので許容する。

## メッセージの形式

1 行 1 通の JSON で、外形は JSON-RPC 2.0 に合わせる。

```json
{"jsonrpc":"2.0","id":1,"method":"status","params":{}}
{"jsonrpc":"2.0","id":1,"result":{"protocolVersion":1}}
{"jsonrpc":"2.0","id":1,"error":{"code":-32001,"message":"モーダルのダイアログが開いています。","data":{"code":"modalDialogOpen"}}}
```

JSON-RPC 2.0 に合わせるのは、段階 5 の MCP が JSON-RPC 2.0 で、変換が素直になるためである。
録画プロセスとの通信のように `type` で判別する形にすると、要求 ID とエラーの形を自前で決め直すことになる。

- `id` は CLI が採番する。`id` の無い行(通知)は、受け取った側が無視してよい。本体からの通知を後から足せるようにするためである。
- `error.code` は JSON-RPC の決まりに従う。-32700 と -32600 から -32603 は JSON-RPC の定めるエラー、アプリのエラーは -32000 から -32099 の範囲を使う。`error.data.code` に CLI の `error.code` と同じ英字の識別子を入れ、CLI はそれをそのまま自分の `error.code` に写す。
- 版は `hello` の `protocolVersion` で確かめる。合わなければ、CLI が `protocolMismatch` で止める。
- JSON のプロパティは camelCase とし、録画プロセスとの通信と同じく、ソース生成のシリアライザと行の読み取りを使う。

段階 4 で使うエラー番号は次のとおりである。

| `error.code` | `error.data.code` | 意味 |
|---|---|---|
| -32700 | `parseError` | JSON を解析できない |
| -32600 | `invalidRequest` | 要求の形式が正しくない |
| -32601 | `methodNotFound` | メソッドが未実装か不明 |
| -32602 | `invalidParams` | 引数の形式か値が正しくない |
| -32603 | `internalError` | 要求を処理できない |
| -32001 | `busy` | `waitFor` の同時実行数が上限に達した |
| -32002 | `timeout` | `waitFor` の期限が切れた |
| -32003 | 状態に応じた識別子 | 現在の状態では要求を受け付けられない |

`-32003` の `error.data.code` には、`rejectedWhileModal`、`rejectedWhileSelection`、`rejectedDuringCountdown`、`rejectedDuringUpdate`、`selectionNotOpen` のいずれかを入れる。

## メソッド

| メソッド | 役割 | 受け付ける条件 |
|---|---|---|
| `hello` | 版とプロセス ID を返す | 常に |
| `status` | 状態を返す | 常に |
| `waitFor` | 状態が条件を満たすまで待って返す | 常に |
| `perform` | `RecorderAction` の動作を始める | 下の「受け付けの判定」による |
| `selection` | 開いている選択画面を、範囲、ウィンドウ、取り消しのどれかで完了させる | 選択画面が開いているときだけ |
| `exit` | 本体を終了する | 下の「受け付けの判定」による |

メソッド名は CLI のサブコマンド名と一致させる(`remote status` は `status`)。

### status

返すものは次のとおりである。

- `recording`：録画の状態(`VideoRecordingState` の名前)、カウントダウンの残り秒数、選択中か
- `screenshotInProgress`、`exitRequested`
- `menu`：トレイメニューの一時停止と再開、停止の有効と無効、一時停止と再開の表示名。Core の `RecordingUiActions` から作り、トレイメニューと同じ判断にする。
- `shortcuts[]`：各動作の割り当てと有効か、登録に失敗したか
- `directories`：静止画と動画の保存先と、確認済みか
- `ui`：設定画面、更新のダイアログ、保存先の確認ダイアログ、選択画面、操作バーのそれぞれが開いているか。モーダルのダイアログが開いているか。カウントダウンは、録画の開始前と静止画の撮影の遅延の両方にあるので、`ui.countdown` に種類(`recording` か `screenshot`)と残り秒数を入れる。
- `lastCapture`：直近の撮影結果を 1 件返す。静止画と録画の保存完了、または保存せずにクリップボードへコピーした結果を記録する。
- `lastFailure`：直近の撮影か録画の失敗通知を 1 件返す。
- 種類は静止画が `screenshot`、録画が `recording` である。どちらも時刻と通知の文言を含み、保存先か失敗したファイルのパスが分かる場合は `path` を含む。
- 保存時の通知を表示しない設定では `lastCapture.notification` は `null` になる。まだ結果がない項目も `null` を返す。

### waitFor

条件(録画の状態、`lastCapture` が指定の時刻より新しいか、など)と期限を受け取り、本体の側で条件を満たすまで待ってから `status` と同じ内容を返す。
期限を過ぎたら `timeout` のエラーを返す。

受け付ける状態は `idle`、`countdown`、`preparing`、`recording`、`paused`、`saving` である。
CLI の既定の期限は 30 秒、指定できる範囲は 1〜3600 秒とする。
`captureAfter` を指定した場合は、`lastCapture.at` がその日時より後になったときに条件を満たす。
日時は ISO 8601 形式で指定する。

UI スレッドで待つと UI が止まり、状態も変わらない。
このため、条件の評価だけを UI スレッドで行い、満たさなければ状態の変化の通知(録画の表示の更新、保存の完了と失敗)に登録して UI スレッドを離れ、変化のたびに評価し直す。
`waitFor` を待っている間、その接続では他の要求を送れない。ほかの要求は別の接続から送る。
同時に待てる `waitFor` は 3 本までとし、4 本目は `busy` で断る。接続の枠を 1 本残し、`status` と `exit` を送れるようにするためである。要求を送らない接続が残りの枠をふさいでも、行の期限で閉じるので、長くても期限の間だけ待てば送れる。

CLI は 1 回の要求で終わるので、状態の変化を購読する仕組みは作らない。ポーリングより CLI が単純になり、診断ログも増えない。

### perform

`RecorderAction` の名前(camelCase)を受け取り、`TrayApplicationContext.PerformAction` へ渡す。
名前は `status` の `shortcuts[]` が返す 8 種類と一致させる。
引数は `{"action":"screenshotFullScreen"}` の形で渡す。
応答は「受け付けた」ことだけを返す。動作の結果は `status` と `waitFor` で見る。
`PerformAction` は選択画面や保存先の確認で人の操作を待つ分岐を持ち、終わるまで数十秒かかりうるためである。
成功の結果は `{ "accepted": true }` とする。

### selection

範囲とウィンドウの選択は、選択画面を実際に開き、その完了を `selection` で送る。
目的が選択画面の流れを確かめることなので、画面を飛ばさずに開くほうが合う。選択画面にはすでに、範囲の始点と終点、取り消しの処理がある。これを本体の側から呼べるようにする。

選択画面は静止画の撮影と録画の両方から開かれるが、同時に 2 つ開かないことは、撮影中と録画の選択中を断る既存の判定で保証されている。
このため、選択画面の側に「いま開いている選択」を 1 つだけ持たせ、`selection` はそれを完了させる。

引数の `kind` で選択方法を指定する。

- `rect` は `{"kind":"rect","x":0,"y":0,"width":320,"height":240}` の形で仮想画面の物理ピクセルを指定する。範囲全体が 1 つのモニター内に収まる必要がある。
- `window` は `{"kind":"window","hwnd":1234}` の形でウィンドウハンドルを指定する。選択画面がその時点で候補として受け付けるウィンドウである必要がある。
- `cancel` は `{"kind":"cancel"}` を送り、選択画面を取り消す。

選択画面が開いていない要求は `selectionNotOpen` で断る。
範囲かウィンドウをその選択画面で受け付けられない場合は `invalidParams` で断る。
成功の結果は `{ "accepted": true }` とする。

選択画面を飛ばして範囲を直接渡す方式は、ウィンドウを直接指定する既存の経路と同じ形で後から足せる。この段階では作らない。

### exit

本体の終了の要求(トレイメニューの「終了」と同じ経路)を行う。テストの後始末に使う。

選択画面が開いていれば、先にその選択を取り消してから終了の要求を行う。
本体の終了の要求は選択の完了を待つので、取り消さないと、人が選択画面を操作するまで本体が終わらないためである。

本体は `exit` の要求 ID への成功の応答を送り終えてから、終了の処理を進める。
CLI は、その応答を受け取れば成功とする。応答より前に接続が切れた場合だけ `disconnected` を返す。
成功の結果は `{ "accepted": true }` とする。

## 受け付けの判定と UI スレッド

パイプの読み取りは UI スレッドの外で行い、要求ごとに UI スレッドへ渡して結果を待つ。
UI スレッドへの受け渡しは `BeginInvoke` を使う。モーダルのダイアログが開いている間も、そのメッセージループで実行されるので、要求は届く。

受け付けの判定は、状態を入力に取る Core の純粋な関数にまとめ、単体テストで確かめる。

| 状態 | 受け付けるメソッド |
|---|---|
| モーダルのダイアログが開いている | `hello`、`status`、`waitFor`、`exit`。ほかは `rejectedWhileModal` |
| 選択画面が開いている | 上に加えて `selection`。ほかは `rejectedWhileSelection` |
| カウントダウン中 | `hello`、`status`、`waitFor`、`exit`、`perform`(停止だけ。下の注記を参照)。ほかは `rejectedDuringCountdown` |
| 更新のダウンロードと準備中 | `hello`、`status`、`waitFor`、`exit`。ほかは `rejectedDuringUpdate` |
| それ以外 | すべて |

複数の状態が同時に該当する場合は、モーダル、選択画面、カウントダウン、更新の順で判定する。
`selection` はこれらの状態に該当せず、選択画面も開いていないとき `selectionNotOpen` で断る。

- `exit` は常に受け付ける。本体の終了の処理は、開いている保存先の確認ダイアログを閉じてから終わる作りなので、テストが途中のダイアログで止まったときの後始末に使える。
- 録画のカウントダウン中の停止は、カウントダウンの取り消しとして働く(本体のトレイメニューの停止と同じ)。静止画の撮影の遅延は本体でも取り消せないので、その間の停止は、停止できる録画が進行しているときだけ受け付けて録画を止め、それ以外は `rejectedDuringCountdown` で断る。選択画面が開いている間の停止は何もしないので、選択の取り消しには `selection` の取り消しを使う。
- モーダルのダイアログは、保存先の確認ダイアログと、設定画面が開く 3 種(診断ログの方針の説明、メッセージボックス、フォルダーの選択)である。保存先の確認ダイアログは本体が追跡しているので、その有無で判定する。設定画面が開く 3 種は開いている画面の一覧に現れないので、設定画面が「モーダルを表示中」を自分で持ち、`status` に写す。保存先の確認ダイアログは設定画面を親に開くことがあるが、設定画面の側では数えない。

設定画面と更新のダイアログは非モーダルで、開いている間もトレイとホットキーが効く。このため、これらが開いているだけでは操作を断らない。

## 更新と終了

本体の終了の処理の先頭で、パイプを閉じる。接続中の相手には、終了を知らせる通知(`id` の無い行)を 1 行送ってから閉じる。
`exit` 以外の要求を待っている間に接続が切れたら、CLI は `disconnected` を返す。

更新は、新しいプロセスが古いプロセスの終了と多重起動のミューテックスの解放を待ってから置き換える。パイプは終了の処理で先に閉じるので、この順序と衝突しない。

## 診断ログ

タグ `automation` を足す。
記録するのは、接続と切断(接続元のプロセス ID)、要求のメソッドと動作の名前、断った理由、応答の成否である。
範囲の座標は記録してよい。ウィンドウのタイトルは記録しない([design.md](design.md)「診断ログ」の方針のとおり)。

`status` と `waitFor` はデバッグのレベル、それ以外は情報のレベルで記録する。
AI が状態を繰り返し読んでも、既定の記録レベルの利用者のログを押し出さないためである。

## CLI のコマンド

`remote` のサブコマンドとして足す。

- `remote status`
- `remote wait --state <状態> [--capture-after <日時>] [--timeout <秒>]`
- `remote perform <動作>`
- `remote select (--rect <x,y,w,h> | --window <hwnd> | --cancel)`
- `remote exit`

本体が起動していなくても、`remote` は本体を起動しない。起動すると、テストの後にトレイが残るためである。
パイプが存在しないとき、本体の多重起動防止のミューテックスが存在すれば `automationDisabled`、存在しなければ `notRunning` を返す。前者のメッセージは、自動化用の接続を受け付ける設定をオンにして保存するよう案内する。
パイプが無い状態で接続を試しても期限まで待つだけになるため、CLI は接続を試す前にこの区別を行い、待たずに返す。
ミューテックスは `Local\` の名前なので、判定できるのは CLI と同じ Windows のセッションの本体だけである。別のセッションの本体は、今までどおり `notRunning` になる。
本体の起動直後はミューテックスを取得してからパイプを作るまでの短い間があり、この間は `automationDisabled` を返す。
どちらも終了コードは 3 とする([automation-cli.md](automation-cli.md)「終了コード」)。
`remote` の各コマンドも、ほかのコマンドと同じコマンドの定義の表に置く。段階 5 の MCP の道具の一覧を、機械的に作れるようにするためである。
MCP は長く動き続けるので、`remote` は要求ごとに接続を開いて閉じる。本体が受け付ける接続の数には上限があるので、MCP が接続を握り続けると、その分だけ CLI が使える接続が減るためである。

## テスト

- Core：メッセージの往復、不正な JSON、受け付けの判定の単体テスト。
- Capture：パイプのサーバーを「名前を受け取り、接続を受け、行を処理の関数へ渡す」だけの部品にする。テストでは名前を GUID にして、同じプロセスのクライアントで接続する。`FirstPipeInstance` の二重生成、複数の接続の同時処理、`waitFor` の本数の上限、行の期限を過ぎた接続を閉じること、上限を超える行、切断、再接続を確かめる。画面は要らないので、既定のテストで回る。
- CLI：`remote` の各コマンドを、偽の処理を持つサーバーを相手に、プロセスを起動せずに確かめる。接続先のプロセスの確認は、CLI の環境(`CliEnvironment`)から差し替えられる境界に置き、このテストでは確認の結果を与える。OS から接続先を確かめる経路は、Capture のテストで、同じプロセスのサーバーについて自分のプロセス ID と実行ファイルが返ることで確かめる。
- 実機：`SCREENRECORDER_TEST_DATA_DIR` をテスト用の一時フォルダーに設定して本体を起動し、`remote status`、`remote perform screenshotFullScreen`、`remote wait --state idle --capture-after <開始前の日時>`、`probe`、`remote exit` を通す。すでに本体が常駐していればスキップし、実行ファイルが見つからなければ失敗する。

## 段階の分け方

| 段階 | 内容 | 完了条件 | 工数 |
|---|---|---|---|
| 4a | この資料 | 資料がレビューを通る | 1〜2 日 |
| 4b | 設定の項目、パイプのサーバー、`hello`、`status`、`waitFor`、CLI の `remote status` と `remote wait` | Core、Capture、CLI のテストが通り、本体を起動して状態を読める | 5〜7 日 |
| 4c | 受け付けの判定、`perform`、`selection`、`exit`、CLI の `remote perform`、`remote select`、`remote exit` | 8 つの動作と選択の完了が、実機の手順で通る | 5〜7 日 |

4b に CLI の最小のコマンドを含めるのは、CLI で状態が見えないと、実機の確認の手順を書けないためである。
