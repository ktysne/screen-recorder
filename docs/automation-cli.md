# 自動化用 CLI と AI からの利用

状態：段階 1〜3 実装済み。段階 4 と 5 は未着手。

この資料は、AI エージェント(Claude Code、Codex)が ScreenRecorder の開発、テスト、利用者の支援に使う仕組みの設計を定める。
アプリ本体の仕様の正本は [design.md](design.md) で、この資料は本体に足す部品と CLI の約束だけを扱う。

## 使う場面

仕組みを使う場面は次の 3 つである。

- **開発**：録画と撮影に関わる変更の結果を、トレイの操作なしで確かめる。対象の範囲の計算(モニター相対の座標、DPI、偶数への丸め)や、出来上がった MP4 の解像度、長さ、音声の有無を AI が確かめられるようにする。
- **テスト**：録画プロセスを起動して数秒録り、ファイルを検査するまでを通すテストを、実機で 1 コマンドで回せるようにする。
- **利用者の支援**：届いた診断ログと設定ファイルを AI が読み、原因の候補を説明する。

録画と撮影は画面とデバイスに依存するので、CLI でも実機でしか動かない。
一方で、設定とログの読み取り、ファイル名の計算、録画済みファイルの検査は、録画を実行しなくてもできる。
段階はこの区別に沿って分ける。

ホットキー、トレイメニュー、範囲の選択画面、録画中の操作バーといった操作感は、段階 4 で扱う。

## 方式の比較

| 方式 | 採否 |
|---|---|
| 別の実行ファイルとしての CLI | 採る(段階 1〜2) |
| アプリ本体の CLI モード | 採らない |
| 起動中の本体の遠隔操作 | 採る(段階 4) |
| MCP | 採る(段階 5、CLI と段階 4 の後) |
| アプリ内 AI アシスタント | 採らない |

CLI を先に作る理由は 3 つある。
第一に、MCP は通信の約束事で、中身として UI なしで動く処理が要る。CLI を作ればその処理ができあがり、MCP は薄く包むだけで済む。
第二に、Claude Code も Codex もシェルから同じように CLI を使える。
第三に、テストから呼べる。MCP だけだと、テストに MCP のクライアントが別に要る。

本体の CLI モードを採らないのは、`ScreenRecorder.exe` が `WinExe`(GUI サブシステム)で、標準出力を呼び出し元のコンソールに返すのが難しいためである。
`AttachConsole` で親のコンソールにつなぐと、シェルがプロンプトを先に返し、出力が後から混ざる。
加えて、本体の `Main` はすでに `--apply-update` と `--record-worker` を振り分けていて、多重起動の判定もここで行う。自動化の入口をここに足すと、多重起動の判定との順序を誤ったときに常駐中の本体と衝突する。

アプリ内 AI を採らないのは、API キーの扱い、利用者の画面やログの外部送信、利用料の負担先という、録画アプリの価値と別の設計が要るためである。
[design.md](design.md)「診断ログ」の、ログを外部へ送らない方針とも衝突する。

## 構成

### プロジェクト

| プロジェクト | 種別 | 役割 |
|---|---|---|
| `ScreenRecorder.Core` | 既存 | 判断の処理。CLI 用に、副作用のない設定の検査、ログの解析、録画の開始データの組み立てを足す |
| `ScreenRecorder.Capture` | 新設(段階 2) | 録画プロセスの起動と制御、保存の確定、動画の後処理、撮影 |
| `ScreenRecorder.App` | 既存 | トレイ、画面、ホットキー。録画プロセスの本体(`--record-worker`)もここに残す |
| `ScreenRecorder.Cli` | 新設(段階 1) | 実行ファイル `screenrecorder-cli.exe` |

`ScreenRecorder.Cli` は `OutputType` を `Exe` にし、モニターの列挙に `Screen` を使うため `UseWindowsForms` を有効にする。
本体と同じ PerMonitorV2 の DPI 宣言をマニフェストに置く。宣言が無いと、DPI が 100% でないモニターの位置と大きさが仮想化された値で返り、本体の計算と食い違う。

### ScreenRecorder.Capture の切り出し

`ScreenRecorder.Capture` は、いま `ScreenRecorder.App` の `internal` にある処理を集めて作る。移した後、`ScreenRecorder.App` はこのライブラリを参照して同じ処理を使い、挙動は変えない。
移す処理は、そのまま移せるものと、他の処理から抜き出す必要があるものに分かれる。

そのまま移せるもの：

- `IRecordingEngine` と `RecordingWorkerProcessEngine`
- `FfmpegVideoRecordingPostProcessor`
- `DesktopCapture`、`AudioEndpoints`
- 上の処理が使う `NativeMethods` の宣言(ファイルを分ける)

抜き出す必要があるもの：

- 録画を最終の名前へ移す処理(`VideoRecordingController` の中で、録画中の状態の記録と結び付いている)
- 静止画の保存(`ScreenshotCaptureService` の非公開の処理で、範囲の選択と同じクラスにある)
- モニターと範囲と設定から録画の開始データを組み立てる処理(`VideoRecordingController.StartRecordingAsync` の中にある)。モニターの情報を引数で受け取る純粋な関数にして Core に置き、`ScreenRecorder.Capture` はモニターの列挙だけを受け持つ
- ウィンドウを録画の対象にできるかの判定(`CaptureSelection` の中にある)
- 録画中のスリープの抑止(`VideoRecordingController` の中にある)。CLI の `record` も、録画の開始から保存の完了まで抑止し、成功、失敗、中断のどの経路でも解除する

移すときに、次の 3 点を引数で受け取る形に変える。

- **ffmpeg の場所**：いまは自分の exe のフォルダーを基準に `ffmpeg\ffmpeg.exe` を探す。CLI から使うと CLI の exe の横を探してしまうので、`ScreenRecorder.exe` のフォルダーを渡す。
- **記録レベル**：`RecordingWorkerProcessEngine` は static な `DiagnosticLog.Level` を読んで録画プロセスに渡している。コンストラクタで受け取る。
- **開始までの時間**：いまはデバッグのログにしか出ない。CLI が結果として返せるよう、エンジンの戻り値かイベントで受け取れるようにする。

録画プロセスの本体(`RecordingWorkerProgram`、`ScreenRecorderLibRecordingEngine`)は `ScreenRecorder.App` に残す。録画プロセスは本体と同じ exe で動く設計([design.md](design.md)「録画プロセス」)で、CLI も `ScreenRecorder.exe --record-worker <パイプ名> <記録レベル>` を起動して録画する。

切り出さずに済ませる案は 2 つあり、どちらも採らない。

- **CLI が `ScreenRecorder.App` を直接参照する案**：実行ファイルのプロジェクトを実行ファイルから参照すると、発行時に両方の実行時構成が衝突し、CLI にトレイと画面のコードが入る。ソースファイルを CLI 側でも読み込む形にすると、同じ型が 2 つのアセンブリにでき、片方だけの修正が起きやすい。
- **CLI が Core の録画プロセスの約束だけを使って自分で話す案**：Core には通信の形式と状態遷移(`RecordingWorkerProtocol`、`RecordingWorkerSession`)があるので成り立つ。しかし、録画プロセスの起動、接続、強制終了、期限の管理を CLI に作り直すことになり、本体と CLI で録画の挙動がずれる。CLI で確かめた結果が本体の挙動の確認にならなくなる。

`docs/development.md` が触れている `tests/ScreenRecorder.Capture.Tests` は、このライブラリのテストとして段階 2 で作る。

### 録画プロセスの見つけ方

CLI は `ScreenRecorder.exe` を次の順で探す。

1. `--app <パス>` で指定されたもの
2. CLI と同じフォルダーにあるもの
3. 開発時のビルド出力(`src/ScreenRecorder.App/bin/<構成>/...`)。リポジトリの中から実行したときだけ探す

見つからなければ、終了コード 3 と `error.code = "appNotFound"` を返す。

## 共通の約束

### 出力

- 標準出力には JSON を 1 つだけ書く。先頭のプロパティは `cliVersion` とする。
- 標準出力は BOM なしの UTF-8 で書き、日本語を `\u` でエスケープしない。
- 人が読む形は `--text` を付けたときだけ出す。
- JSON の基本形は `{ "cliVersion": "...", "command": "logs show", "result": {}, "warnings": [], "error": null }` とする。検査対象に問題がある場合は `result` に問題を含め、終了コード 1 を返す。CLI が処理できない場合は `result` を `null` にし、`error` に識別子と日本語の説明を入れる。
- 知らせるべきことは `warnings[]` に、エラーは `error.code` と `error.message`(日本語)に入れる。`error.code` は英字の識別子で、AI とテストはこちらで判断する。
- 時刻は ISO 8601 の地方時とオフセット、長さはミリ秒の整数で書く。プロパティ名は camelCase とする。
- 設定の検査結果は `issues[]` に識別子、項目名、説明を入れる。`defaultedProperties[]` には既定値を補った設定項目名を camelCase で入れる。

### 終了コード

| コード | 意味 |
|---|---|
| 0 | 成功。検査のコマンドでは問題なし |
| 1 | 検査で問題あり(設定の値が範囲外、動画の長さが期待と違う、など) |
| 2 | 引数の誤り |
| 3 | 読み書き、撮影、録画の失敗 |

1 と 3 を分けるのは、「対象に問題がある」と「CLI が仕事をできなかった」を AI が取り違えないためである。

### 副作用

- 入力のファイルを書き換えない。設定ファイルを読むときも、`SettingsRepository.Load` を使わない。`Load` は壊れた JSON を見つけると `.bak` を書いて既定値を返すので、検査のつもりで利用者のフォルダーに書き込んでしまう。
- 既存のファイルは `--force` が無ければ上書きしない。
- 本体の設定ファイルは書かない。
- 多重起動のミューテックスを取らない。常駐中の本体と同時に動かせる。

### 診断ログ

CLI 自身は診断ログのフォルダーにログを書かない。
本体は起動ごとにログを 1 本作り、10 本を超えた古いものを消すので、CLI がここに書くと利用者のログを押し出す。

CLI は `DiagnosticLog.SetForwarder` で、自分のプロセスと録画プロセスから届くログを集め、JSON の `log[]` に入れて返す。
録画プロセスに渡す記録レベルは `--log-level` で選び、既定は `info` とする。

録画プロセスは、接続する前の失敗と、接続が切れた後のログを、共有のフォルダーの `record-worker-orphan.log` に書く(本体から起動したときと同じ動作)。`--app` に誤った exe を渡したときも、ここに書かれうる。
テストや不具合の調査では `--log-level debug` を使う。録画ライブラリの詳細はデバッグのレベルでしか出ない行がある。
CLI が途中で止められると録画プロセスはこの状態になるので、CLI は Ctrl+C を受けたら録画プロセスに停止を送り、書き終えを待ってから終わる。

### 常駐中の本体との同時実行

- CLI の `record` は、録画中の一時ファイルに本体と違う名前(`<名前>.<GUID>.cli-partial.mp4`)を使う。本体は起動時に保存先の `*.recording.mp4` を未完了の録画として知らせるので、同じ名前を使うと、CLI の失敗の残骸を本体が利用者に知らせてしまう。
- 一時名は録画ごとに一意にし、既存のファイルには書き込まない。CLI の残骸は誰も片付けないので、`record` は `-o` のフォルダーに `*.cli-partial.mp4` を見つけたら `warnings[]` でパスを知らせる。
- 同じモニターを 2 つの録画プロセスが同時に録画できる。本体と CLI の録画は同じ録画プロセスを使うので、CLI の `record` を 2 つ同時に動かして、両方の動画が期待の長さと解像度で保存されることを確かめた(主モニター 3840x2160、Windows 10)。このため `record` は本体の録画中を断らない。
- 本体の更新は配布物の exe と DLL を置き換えるので、CLI が録画プロセスを動かしている間は更新が失敗しうる。当面は CLI を配布しないので、影響は開発者の手元に限られる。

## コマンド

引数の正本は `screenrecorder-cli help` の出力とし、この資料には各コマンドの役割と主な引数だけを書く。

### 段階 1：読み取りと計算

`ScreenRecorder.Core` と、モニターの列挙に使う `Screen` だけで作る。`ScreenRecorder.Capture` は要らない。モニターごとの DPI は `Screen` から取れないので、`GetDpiForMonitor` の宣言を CLI が持つ。

- `info`：CLI の版、本体の設定ファイルとログのフォルダーの場所、既定の動画と静止画の保存先、モニターの一覧(デバイス名、位置、大きさ、DPI、主モニターか)。
  モニター情報には、仮想画面上の位置と大きさ、作業領域、横と縦の DPI、主モニターかどうかを含める。DPI を取得できないモニターは `dpi.x` と `dpi.y` を `null` にし、警告を返す。
- `settings show [--file <パス>]`：設定を読んで、既定値を補った結果を返す。どの項目が既定値を補ったものかも示す。
- `settings validate [--file <パス>]`：JSON として壊れていないか、値が範囲外でないか、知らない項目やショートカットの重複がないかを検査する。問題があれば終了コード 1。`Load` は範囲外の値を黙って既定値に戻すので、検査は Core の既存の検査(`SettingsValidator`、`ShortcutSettingsValidator`)を土台に、`Load` とは別の処理として Core に置く。
- 設定ファイルが無い場合は組み込みの既定値を使う。明示した `--file` が無い場合は終了コード 3 を返す。設定の読み取りは `.bak` を作らず、値を補った項目と検査結果を返す。
- `logs list`：ログのファイルの一覧(開始時刻、大きさ、ヘッダーの版)。
- `logs show [<ファイル>] [--since <日時>] [--level <レベル>] [--tag <タグ>] [--grep <文字列>] [--limit <件数>]`：ログを 1 行ずつ解析して返す。ファイルを省くと最新の 1 本を読む。本体は書き込み中のファイルを共有読み取りを許して開いているので、書いている最中でも読める。
- `logs show` の `--level` は指定したレベル以上(error が最も重い)を返し、`--limit` は条件に合う行のうち末尾から数えた件数で、既定は 200 とする。全行をメモリに載せず、1 行ずつ読んで返す分だけを残す。条件に合った行の総数は `matchedCount` で返す。
- ログの時刻はファイル名と行の時刻をローカル時刻として解釈し、その日時のローカルオフセットを付けて返す。書式に合わない行も `rawLine` に保持する。
- `naming preview [--template] [--mode] [--window] [--at] [--dir]`：保存するファイル名と月別フォルダーの結果を返す。`--dir` は設定の保存先を上書きする。
- `help [<コマンド>]`：既定は JSON。

### 段階 2：録画、撮影、検査

段階 2a で録画の処理を `ScreenRecorder.Capture` へ切り出して `record` と `probe` を、段階 2b で撮影の処理を切り出して `screenshot` を足す。
録画を先にするのは、録画プロセスを使う経路のほうが本体で確かめにくく、CLI の効果が大きいためである。

- `record -o <MP4> --duration <秒> (--display <n> | --rect <x,y,w,h> | --window <hwnd>) [--pause-at <秒> --resume-at <秒>] [--settings <パス> | --defaults] [--app <パス>] [--force] [--log-level <レベル>]`：録画プロセスを起動して指定の実時間だけ録り、最終の名前へ移す。
  カウントダウン、操作バー、範囲の枠は出さない。
  `--duration` は一時停止時間を含み、`--pause-at` と `--resume-at` は両方を指定する。
  結果には `app`、`target`、`startData`、`temporaryPath`、`finalPath`、`retainedPath`、`timings`、`requestedDurationMs`、`expectedVideoDurationMs`、`timeoutMs`、`pause`、`interrupted`、`log` を含める。
- `--rect` は仮想画面の座標で指定し、1 つのディスプレイに収まらなければ終了コード 2 で断る。本体の選択画面も矩形を 1 つのディスプレイに収めていて([design.md](design.md)「撮影対象の決め方」)、録画プロセスは 1 つのディスプレイを相手に範囲を切り出すためである。選択画面のように切り詰めないのは、指定と違う範囲を黙って録らないためである。
- `record --dry-run ...`：録画プロセスを探さず、開始データ、対象範囲、ディスプレイ範囲、選んだモニターを返す。
  `--rect` はモニター相対の範囲へ変換される。
- `probe <ファイル> [--expect-width <px>] [--expect-height <px>] [--expect-fps <fps>] [--expect-duration-ms <ms>] [--tolerance-ms <ms>] [--expect-video-codec <名称>] [--expect-audio-channels <数>] [--expect-audio-rate <Hz>] [--expect-no-audio]`：MP4 と PNG を検査する。
  MP4 は長さ、解像度、フレームレート、映像と音声のコーデック、音声のチャンネル数、サンプリングレート、ビットレートを返す。
  PNG は幅と高さを返す。
  期待値との差は `result.mismatches[]` に入り、終了コードは 1 になる。
- `probe <MP4> --frame <秒> -o <PNG> [--force]`：指定時刻のフレームを PNG に書き出す。
  既存の出力は `--force` を指定したときだけ上書きする。
- `screenshot -o <パス> (--display <n> | --rect <x,y,w,h> | --window <hwnd>) [--settings <パス> | --defaults] [--force]`：静止画を 1 枚撮って保存する。範囲の選択画面は出さない。
  対象の指定、設定の読み取り、`--rect` が 1 つのモニターに収まること、`--window` の撮影可否は `record` と同じ規則で判定する。
  保存形式は出力先の拡張子で決め、PNG、JPEG を選べる。圧縮、品質、カーソル合成は設定に従う。
  撮影の遅延、カウントダウン、クリップボードへのコピー、撮影後の動作、通知は行わない。
  結果には `path`、`format`、`width`、`height`、`target`（種類、モニター、範囲）を含める。
  既存の出力は `--force` がある場合だけ置き換え、撮影画像を一時ファイルへ書き終えてから移す。
  引数の誤りは終了コード 2、撮影失敗は `captureFailed`、保存失敗は `saveFailed` として終了コード 3 を返す。
  `--force` の無い既存ファイルは `outputExists` として終了コード 2 を返す。

`record` は数秒の録画でも実時間がかかる。
CLI は全体の期限を「録画の長さ + 準備の期限 + 書き終えの期限」とし、その値を結果の JSON に書く。呼び出す AI が、自分のツールの待ち時間をこれに合わせられるようにするためである。

録画の設定(fps、ビットレート、カーソル、ハードウェアエンコード、音声)の既定は、本体の設定ファイルの値とする。利用者の環境で起きた問題を同じ条件で再現することを優先するためである。
`--settings <パス>` で別の設定ファイルを、`--defaults` で組み込みの既定値を使える。テストは `--defaults` か、リポジトリに置いた設定ファイルで回す。

`probe` は Media Foundation で読む。
同梱の `ffmpeg.exe` は MP3 を選んだときにしか使わない任意の部品なので、検査をこれに頼らない。

### 段階 3：AI への伝え方

- リポジトリの `CLAUDE.md` と `AGENTS.md` に CLI への参照を 1 行置き、`.claude/skills/screenrecorder-cli/SKILL.md` に場面ごとのコマンドを書く。引数は `help` が正本なので Skill には写さない。

### 段階 4：起動中の本体の操作

トレイ、ホットキー、選択画面、操作バーの流れを AI が確かめるには、常駐中の本体を操作する経路が要る。
ここには方向性だけを書き、通信の形式と安全性は段階 4 の最初に別の資料で決める。

- 設定で有効にしたときだけ、現在のユーザーに限った名前付きパイプを本体が開く。作り方は録画プロセスとのパイプ(`PipeOptions.CurrentUserOnly`、1 行 1 通の JSON、行の上限)に合わせる。
- 操作の一覧は `RecorderAction` から作り、実行は `TrayApplicationContext.PerformAction` と同じ経路を通す。
- 状態の取得(録画の状態、保存先、直近の保存ファイル)を先に作り、操作は後から足す。
- 要求は UI スレッドで実行し、設定画面やダイアログが開いている間は状態の取得だけを受け付ける。

### 段階 5：MCP

段階 4 の後に作る。
開発の場面ではシェルがあるので要らない。効くのは、シェルを持たないクライアント(Claude Desktop など)から撮影や録画、起動中の本体の操作を頼む場面である。
`screenrecorder-cli mcp` のサブコマンドとして標準入出力で動かし、道具の一覧は CLI のコマンドから作る。Node などの別の実行環境を利用者に求めずに済むためである。

## テスト

- 段階 1 で Core に足す処理(設定の検査、ログの解析)と段階 2a で Core に移す開始データの組み立ては、`tests/ScreenRecorder.Core.Tests` に単体テストを足す。開始データの組み立ては、DPI が 100% でないモニターや、主モニターの左や上にあるモニターの座標を入力に含める。
- CLI の引数、出力、終了コードは、新しい `tests/ScreenRecorder.Cli.Tests` で確かめる。CLI の入口を、引数と標準出力の書き手を受け取る関数にして、テストからプロセスを起動せずに呼ぶ。設定とログは一時フォルダーに置いたものを使う。`DiagnosticLog` は static なので、このテストは並列に実行しない集まりにまとめ、テストごとに転送先を外す。
- 段階 2 の撮影と録画のテストは `tests/ScreenRecorder.Capture.Tests` に置く。GPU と Media Foundation と画面が要るので、環境変数 `SCREENRECORDER_DESKTOP_TESTS=1` があるときだけ実行する。xUnit 2 は実行時にテストを飛ばす手段を持たないので、`Fact` を継承し、環境変数が無いときに `Skip` を設定する独自の属性を作る。`dotnet test ScreenRecorder.slnx` の既定の結果は変えない。
- 実機のテストの最初の 3 本は、主モニターの 3 秒の録画、範囲の 3 秒の録画と一時停止、静止画の撮影とし、`probe` と同じ処理で解像度と長さを確かめる。
- `screenshot --display 0` の PNG、`--rect` の JPEG、一時ファイルから既存画像を置き換える保存処理も `tests/ScreenRecorder.Capture.Tests` で確かめる。
- 実機での確認は PR に手順を書く、という [implementation-plan.md](implementation-plan.md) の運用は変えない。CLI ができた後は、その手順を CLI のコマンドで書ける。

## 配布

当面は CLI を配布物に含めない。開発者と AI が手元のビルドで使う。

含めることにしたときは、次を変える必要がある。

- `build-package.bat` の同梱物の許可リストと、[design.md](design.md)「配布」の一覧。
- 自己完結の単一ファイルで発行すると .NET の実行環境が 2 つの exe に重複して入る。大きさが問題になるなら、CLI を本体に同梱せず別に配る。
- 更新を止める判定に、CLI と録画プロセスが動いていることを入れる。
